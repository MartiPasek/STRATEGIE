1. 🧩 Jak to celé funguje (princip)

Základní myšlenka: Docházka funguje jako spojitá osa — řetězec stavů bez mezer. Každá změna (příchod, pauza, odchod, jednání...) vytvoří nový záznam v tabulce att_entry. Předchozí záznam se automaticky uzavře (dostane status='superseded'). V každém okamžiku má zaměstnanec maximálně jeden aktivní záznam.
👷
Příchod
att_entry: work
→
☕
Pauza
att_entry: break
→
👷
Návrat
att_entry: work
→
🤝
Jednání
att_entry: announced
→
👷
Zpět
att_entry: work
→
🏠
Odchod
att_entry: day_end

Každý rámeček výše = jeden řádek v databázi. Když přijde nový stav, předchozí se automaticky uzavře a spočítají se hodiny.

Analogie pro amatéra

Představ si to jako stopky, které se přepínají. Máš jen jedny stopky najednou. Když zmáčkneš „Pauza", stopky „Práce" se zastaví a stopky „Pauza" začnou tikát. Když zmáčkneš „Zpět do práce", stopky „Pauza" se zastaví a „Práce" zase běží.

Na konci dne se sečtou: kolik tikaly stopky „Práce" = odpracováno.

2. 📅 Jeden den od rána do večera

7:26 — Příchod
Zaměstnanec ťukne „Jsem v práci" → systém vytvoří att_entry typu work.
Stopky začínají tikát. Hlavička: „Dnes makám 😉"
7:26–11:30 — Práce
Záznam běží. Hodiny se počítají průběžně (UI ukazuje živě).
11:30 — Oběd
Ťukne „Pauza — jdu se najíst" → starý work záznam se uzavře (4:04 h).
Nový záznam break začne. Hlavička: „Dávám si pauzu ☕"
12:00 — Návrat
Ťukne „Jsem zpět" → break se uzavře (0:30 h), nový work začne.
14:00 — Jednání (do 15:00)
Ťukne „Mám jednání" s časem „do 15:00" → vytvoří announced záznam.
Směna BĚŽÍ DÁL — jednání je status vedle práce, ne odhlášení.
Hlavička: „Mám jednání do 15:00 🤝"
UI ukáže tlačítka Konec a Prodloužit
15:00 — Jednání skončilo
Ťukne „Konec" (nebo uplyne čas) → announced se superseduje, práce pokračuje.
16:30 — Odchod
Ťukne „Pro dnešek konec" → work se uzavře, vytvoří se day_end záznam (0 hodin, jen značka konce dne).
Hlavička: „Že by dovolená?… 😎" (žádná běžící směna)

Výpočet hodin za den

Systém sečte všechny uzavřené záznamy kategorie „presence" (tj. work, homeoffice, trip, overhead) a odečte pauzy. Výsledek = odpracováno.

Jednání (announced) se do hodin nepočítají zvlášť — probíhají BĚHEM běžící směny.

8. 📋 Plánování směn a fond hodin

Plán má 4 vrstvy — vyšší vrstva vždy přebije nižší:

Vrstva 4 — Osobní NEJVYŠŠÍ PRIORITA
Individuální výjimka pro konkrétního člověka (att_exception_scope scope=user)
Vrstva 3 — Skupina
Výjimka pro celou skupinu (att_exception_scope scope=group)
Vrstva 2 — Firma
Celofiremní výjimka (att_calendar_exception)
Vrstva 1 — Základ NEJNIŽŠÍ
Týdenní rozvrh zaměstnance (work_schedule) + kalendář (att_calendar_day)

Jak se plán generuje

  1. Základ = týdenní rozvrh zaměstnance (Po-Pá 8h, So-Ne 0h...)
  2. Kalendář přebije: svátek → 0 h
  3. Firemní výjimka přebije: „23.12. jen 4h" → 4 h
  4. Skupinová výjimka přebije: „Výroba 24.12. volno" → 0 h
  5. Osobní výjimka přebije: „Petra 24.12. pracuje" → 8 h

Výsledek se uloží do att_plan_effective — to je jediný zdroj pravdy pro „co se čekalo".

Frozen záznamy (is_frozen=true) se při regeneraci nikdy nepřepíšou.

17. ⚖️ Důležitá byznys pravidla

  1. Nepotvrzený den blokuje příchod — zaměstnanec se nemůže píchnout, dokud nepotvrdí (nebo nerozporuje) starší dny.
  2. Jeden aktivní záznam — v každém okamžiku má zaměstnanec max 1 is_active=true záznam.
  3. day_end je záměr, ne chyba — „Pro dnešek konec" vytvoří day_end s 0 hodinami. O půlnoci se automaticky uzavře. Není to zapomenutý odchod!
  4. Jednání/pochůzka ≠ odhlášení — směna BĚŽÍ DÁL, jen se ukazuje status.
  5. REZIE zakázka → overhead — pokud se zakázka změní na REZIE, project_ref se nastaví na NULL a typ na overhead.
  6. Plán: osobní > skupina > firma > základ — a is_frozen=true se nikdy nepřepíše.
  7. Schválení korekce = jedna transakce — výjimka + plán najednou, nebo nic.
  8. Import z Centrály se nekontroluje anomáliemi — zdroj ec_sumaden a centrala1 je vyloučen.
  9. Tenant 2 = EUROSOFT — docházka je hardcoded na tenant 2.
  10. Lokální čas — všechny výpočty v JS používají lokální datum (_locDate()), ne UTC.
